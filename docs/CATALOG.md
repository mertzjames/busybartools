# Publishing to the BUSY Apps Catalog

The [BUSY Apps Catalog](https://github.com/busy-app/busy-apps-catalog) lists apps people can install from the BUSY app
and the bar's web page. A catalog entry is one file, `applications/<app-id>/manifest.yml`, added by a pull request to
that repo. It points at a commit of this repo. The catalog builds the app itself from that commit. There's no
package to upload. Why the repo is laid out this way: [DECISIONS.md R12](DECISIONS.md).

Official guide: <https://docs.busy.app/bar/dev/js-apps/publish-in-catalog>. The rules that matter most here:

- **The build sees only `apps/<app>/app/`**, offline. Nothing in `app/` may import from outside it (the kit is
  vendored; `tools/check.sh` enforces it).
- **App IDs** need at least two dots, and busy-cli caps them at 32 characters. Ours are `io.github.mertzjames.<app>`. An ID can't change
  once published, and updates must come from this repo.
- **The pinned commit must stay reachable**, so it must be on `main`.
- **Every update is a new catalog PR** with a higher `version` and a new commit.
- **Content limits:** short description 10–120 characters, plain text; description 50–4000 and changelog 10–4000, in
  a Markdown subset (`#`/`##` headings, bold, italic, lists, http(s) links; no tables, code, images or HTML); 1–10
  front screenshots, exactly 72×16 PNG.

## What each app needs (all inside `app/`)

| File | Becomes | Notes |
|---|---|---|
| `src/appmeta/manifest.json` | name, ID, version, author | `description` doubles as the catalog's short description (≤ 120 characters) |
| `src/appmeta/icon_*.png` | menu icons | already generated by each app's renderer |
| `CATALOG.md` | description | written for people browsing the catalog, not developers |
| `CHANGELOG.md` | changelog | one `## <version>` section per version; the current one is used |
| `screenshots/*.png` | screenshots | 72×16, captured on a bar; sorted by name, the first is the card cover |
| `package-lock.json` | build | pins `@busy-app/cli` (already true for every app) |

The repo-root `LICENSE` (MIT) covers every app.

## Publishing a new app or version

1. **Prepare the app in a PR to `dev`:**
   - bump `"version"` in `app/src/appmeta/manifest.json`;
   - add its `## <version>` section to `app/CHANGELOG.md`;
   - update `app/CATALOG.md` if the app changed.
2. **Capture screenshots on the bar.** Deploy the app (`tools/deploy.sh <app>`), then run:

   ```bash
   python3 tools/screens.py --count 40 --every 3 --raw --out screens/<app>
   ```

   Look at the LED-style `screen_NNN.png` files and pick 3–6 frames that show the app at its best: the main scene
   first, then a card with live text. Copy their `raw_NNN.png` twins to `app/screenshots/1.png`, `2.png`, ….
3. **Dry-run the checks:**

   ```bash
   python3 tools/catalog.py <app> --worktree --build
   ```

   This checks everything the tool knows about, then builds `app/` alone in a temp folder the way the catalog does
   (`npm ci --ignore-scripts`, then `busy-cli build`).
4. **Merge the PR to `dev`, and promote `dev` to `main`** (maintainers). Then `git fetch origin`.
5. **Write the catalog manifest from the `main` commit:**

   ```bash
   python3 tools/catalog.py <app> --build --out ../busy-apps-catalog/applications/<app-id>/manifest.yml
   ```

   It refuses a commit that isn't on `origin/main`. Pass `--sha <commit>` to pin an older `main` commit, and
   `--category` to choose something other than `art`. The category is fixed by the first published version.
6. **Open the catalog PR** from your fork of `busy-app/busy-apps-catalog`, changing only that one file.
   - Title: `Add <Name> (<app-id>) <version>`, or `Update <Name> (<app-id>) to <version>`.
   - Fill in the template's author checklist yourself. Only tick what's true: you tested the app on a bar, and you
     captured the screenshots there.
   - **AI usage:** these apps were written with an AI coding agent. Choose the matching option and say what the
     generated code does.
7. **Review:** automated checks run on the PR, and a moderator usually answers within 1–2 business days. A PR with no
   response from you for 14 days is closed. After the merge, a bot comments on the PR when the version is live.

## Removing an app

Open a catalog PR that deletes `applications/<app-id>/` and changes nothing else. The ID stays reserved. Bars that
already have the app keep it.

## Not in the catalog

**Wizarding Thanksgiving** (`wizard.thanksgiving`) stays on GitHub Releases only. Its scenes borrow from a well-known
book series, and the catalog rejects apps that infringe third-party rights (R12).
