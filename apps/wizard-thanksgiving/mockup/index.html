    The project

    The BUSY Bar is a small desk and wall display with a 72 × 16 RGB LED front panel, an HTTP API and a JavaScript runtime for apps that run on the device itself. The goal was a screen to hang over a doorway for a Harry Potter–themed Thanksgiving: something festive that changes every few seconds, shows characters walking, flying and interacting, and tells guests the time.

    The whole thing was built in one session with Claude Code. It covered researching the device's undocumented animation format, drawing the pixel art, writing the scenes, building the on-device app, getting through the home network to install it, and tuning everything after seeing it on the wall. Every character is original pixel art that nods to the wizarding world; nothing is copied from official artwork.

    How it works

    1. Draw sprites as text

      Every character is a small grid of letters, one per pixel, in Python. That makes art changes quick to make and easy to review.

    2. Render each scene

      A Python renderer choreographs every frame: flight paths, particles, fire, smoke and text. Builds are deterministic and take about 2 seconds.

    3. Bake into .anim

      Frames are packed into the bar's own animation format. The firmware plays them smoothly with no network traffic.

    4. Run the show on the bar

      A small TypeScript app loops the scenes and draws a live clock from the bar's own time, in a custom gold pixel font.

    This page uses the same rendered frames and the same font tables as the bar. Before deploying, a test checks that the bar app, this preview and the renderer draw the clock identically, pixel for pixel.

    Key decisions

    Each decision is recorded in the project's decision log with its reasoning and the alternatives considered. These are the highlights.

    Architecture

    • D1Runs on the bar itself. An on-device app, not a laptop sending frames, so nothing breaks if a computer sleeps mid-party.
    • D2Every scene is a pre-rendered animation. Firmware playback is smooth. Redrawing over the network tops out around 3 fps.
    • D3One renderer feeds everything. The bar, this page and the storyboards all come from the same frames.
    • D4A small animation writer instead of firmware tooling. Adapted from an MIT-licensed community tool, with a decoder that verifies every file.
    • D14Bundle quirks handled. Generated data lives where the BUSY build packs it into a single script the firmware can run.

    Look and feel

    • D5Original art only. Nods to the theme without copying official characters or logos.
    • D18No black facial details. On LEDs, black is an unlit pixel, so dark glasses read as a third eye. Faces use lit colors.
    • D19Every student wears a different house's colors. All four houses appear once per loop.
    • D21A tone curve brightens the scenes. It lifts dark skies and dim stars while unlit pixels stay off, and the bar keeps its automatic brightness.
    • D22A winged serpent dragon. Its body follows the head's flight path like a snake, and it torches the turkey with a sustained flame.

    Time and date

    • D724-hour clock after every scene. 4.5 seconds of time, then 3.5 seconds of date, so guests always know when to look.
    • D10Custom gold pixel font. Drawn as bitmaps with a gradient and shadow, which the built-in fonts can't do.
    • D15Local time comes straight from the bar. No timezone math, and the minute updates in place.

    Shipping it

    • D9No secrets in the repo. The device password, if one is set, lives in a git-ignored file.
    • D16One-command deploy. Render, build, install and launch, with a fallback to the raw API.
    • D20Verified on the hardware. Screen captures from the bar's own framebuffer confirm each scene and the live clock.
    • D23Quit before reinstalling. Installing over a running app fails and silently uninstalls it.

    The plan, and how it went

    1. Research the device

      Read the BUSY Bar API and app docs, found the community notes on its animation format, and chose an on-device app with pre-rendered scenes.

    2. Plan with mockups as checkpoints

      The plan put a reviewable mockup ahead of any device work, so the direction could be steered early. Three extra scenes joined the original five.

    3. Build the renderer and eight scenes

      Sprites, effects, fonts and an animation writer. Each scene was checked at LED scale before the first mockup went out.

    4. Feedback rounds on the mockup 4 rounds

      The witch became a schoolgirl in robes instead of a Halloween witch. The wizard's "three eyes" became green eyes behind silver glasses. Every student got a different house scarf.

    5. Build the on-device app

      A TypeScript app built with the BUSY toolchain, plus a parity test so the bar's clock matches the preview exactly.

    6. Reach the bar network

      The bar sat on a separate network. Diagnosing it showed traffic stopping at the router. A firewall rule and enabling the bar's Wi-Fi API opened the path.

    7. Tune it on the wall

      Brightened the scenes after seeing them in person, then rebuilt the dragon as a menacing winged serpent. Both changes were verified with screen captures from the bar.

    Lessons from the hardware

    • Black is a hole. On an LED panel, a black pixel is an unlit LED. Details drawn in near-black disappear or read as gaps.
    • Let the firmware animate. Pre-rendered animations play smoothly with zero requests. Pushing frames over HTTP manages about 3 per second.
    • Test against real output. The clock parity test caught a one-step color difference: Python and JavaScript round halves differently.
    • Read the device, not just the docs. Its live API reference, framebuffer captures and remote button presses made testing on the wall fast.
